== Abstract

This document is the official technical specification of the **{doc-name}** standardised
by the **{organization}** (CNA).
It defines, in a language-agnostic way (using a notation inspired by the Kotlin language), the interfaces,
classes, enumerations, errors, structural relationships and behavioural requirements that any conforming
implementation of the {doc-name} MUST satisfy.

The {doc-name} is the *underside* of the *Terminal Reader API* (<<ref_cna_tr,CNA-TR-API>>). It defines the *internal*
contract used by reader implementations and by card extension modules to exchange APDU-level data with cards,
while the *Terminal Reader API* remains the public-facing surface used by terminal applications.

== Introduction

=== Purpose

The {doc-name} defines the *internal* contract by which:

* a *reader implementation* MUST expose an APDU transmission interface (the *proxy reader*) so that selection
  managers and card transaction managers can exchange data with cards in a uniform way,
* a *card extension* MUST expose its selection process (request preparation and response parsing) so that the
  selection manager defined by <<ref_cna_tr,CNA-TR-API>> can drive it,
* APDU-level errors carry the responses already received before the failure together with any duration
  information required to enforce the APDU exchange execution-time bounds.

The API is *internal*: terminal applications MUST NOT use it directly. It is the contract that allows reader
implementations and card extensions written by independent vendors to interoperate.

=== Scope

This specification covers:

* the APDU request and response data carriers, including the per-request duration bound and per-response measured
  duration used to control the APDU exchange execution time,
* the selection request and response data carriers, including the multi-channel-aware channel information,
* the proxy-reader contract through which APDUs are transmitted, including the multi-channel transmission and
  closure operations,
* the SPI implemented by card extensions to drive selection,
* the SPI implemented by card extensions to represent a selected smart card, including the multi-channel variant,
* the family of errors raised at APDU exchange level.

The following topics are *out of scope*:

* the public reader interface exposed to terminal applications (covered by <<ref_cna_tr,CNA-TR-API>>),
* the parsing of APDU payloads (deferred to specific card extension specifications),
* the protocol-level cryptographic security mechanisms handled by card extensions such as the
  Calypso Card API.

=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it raises errors exclusively of the types defined in <<sec_errors>> for the situations described,
. it preserves the structural relationships described in <<sec_architecture>>,
. every object it provides implements the interface of <<ref_cna_tr,CNA-TR-API>> that corresponds to its type,
  as described below.

The Terminal Reader API (<<ref_cna_tr,CNA-TR-API>>) exposes to terminal applications the public-facing facet
of the objects whose internal facet is defined by this specification. An implementation exposes each
contract of this API through an adapter that also implements the corresponding interface of CNA-TR-API:
every object implementing a type of the right column MUST therefore also implement the interface of the left
column.

[cols="^.^1,^.^1", options="header"]
|===
| CNA-TR-API interface     | CNA-TC-API type
| `CardReader`             | <<type_ProxyReaderApi,`ProxyReaderApi`>>
| `CardSelectionExtension` | <<type_CardSelectionExtensionSpi,`CardSelectionExtensionSpi`>>
| `SmartCard`              | <<type_SmartCardSpi,`SmartCardSpi`>>
|===

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
**MAY** and **OPTIONAL** are to be interpreted as described in <<ref_rfc2119,RFC 2119>> and <<ref_rfc8174,RFC 8174>> when, and only when,
they appear in all capitals.

In conformance with <<ref_rfc2119,RFC 2119>>, **SHALL** is equivalent to **MUST**; this specification uses **MUST** exclusively in
order to avoid ambiguity.

Type names follow `UpperCamelCase`; operation, parameter and enumeration-member names follow `lowerCamelCase`
except for enumeration values which use `UPPER_SNAKE_CASE`. Names defined by this specification are reproduced

==== Operation contracts

To avoid repetition, the following rules apply to every operation table in <<sec_specification>> and are therefore
not restated for each operation:

* *Pre-conditions.* The *Pre-conditions* row states what the caller MUST guarantee before invoking the
  operation. Violating one is a contract error, never listed in the *Errors* row, which describes only the
  outcomes a correct caller must handle. Each entry is prefixed by its nature, which determines the error
  raised when the condition is not met:
** *Argument* -- an illegal argument error. Applies to any invalid argument, including values bounded by a card or SAM protocol.
** *Range* -- an index out of bounds error. Applies when the argument designates a position within a collection or memory image exposed by the API.
** *State* -- an illegal state error.
** *Capability* -- an unsupported operation error.
* *Non-`null` results.* Unless the return type is marked nullable (`T?`) or the *Returns* row states otherwise, an
  operation returns a non-`null` value.
* *Collections.* Unless the return type is marked nullable (`T?`), an operation whose return type is a collection
  (e.g. `List`, `Set`, `Map`) returns an empty collection rather than `null`.

==== Concurrency

Unless explicitly stated otherwise, the stateful types defined by this specification are *not* thread-safe. A given
instance MUST be accessed from a single thread at a time; concurrent use of the same instance without external
synchronisation results in undefined behaviour. Distinct instances MAY be used concurrently.

=== Multi-channel design

The {doc-name} exposes the multi-channel capability of ISO/IEC 7816-4 cards through:

* a dedicated SPI sub-type <<type_MultichannelSmartCardSpi,`MultichannelSmartCardSpi`>> that carries the channel
  number of each active smart card,
* dedicated proxy-reader operations
  <<op_ProxyReaderApi_transmitCardRequestAndCloseChannel,`transmitCardRequestAndCloseChannel`>> and
  <<op_ProxyReaderApi_closeChannel,`closeChannel`>> that target a specific channel by passing the corresponding
  `MultichannelSmartCardSpi`.

The single-channel transmission operation <<op_ProxyReaderApi_transmitCardRequest,`transmitCardRequest`>> accepts the base
<<type_SmartCardSpi,`SmartCardSpi`>> and serves both the single-channel and the multi-channel use case (the
implementation extracts the channel information from the dynamic sub-type when needed).

=== APDU exchange execution-time control

This specification allows the execution time of each APDU exchange to be controlled at software level. It
provides:

* an *optional* maximum duration on each request
  (<<type_ApduRequest,`ApduRequest.apduExchangeMaxDuration`>>),
* an *optional* effective duration on each response
  (<<type_ApduResponse,`ApduResponse.apduExchangeDuration`>>),
* a dedicated error, <<type_ApduExchangeDurationExceeded,`ApduExchangeDurationExceeded`>>, raised when the
  effective duration of an exchange exceeds the declared maximum.

The durations exchanged through this specification are expressed in *microseconds*. The effective resolution of
the measurement depends on the reader and on the execution platform: an implementation MUST document the
resolution it provides, and a bound finer than that resolution MUST NOT be relied upon.

This mechanism is a practical way to implement security countermeasures against two threats. Against a *relay
attack*, relaying the dialog with a card to a remote location adds a transmission delay; an abnormally long exchange
can therefore reveal that the card is not actually present in front of the reader. Against *card emulation*, a
generic RFID device answering in place of the expected card processes the command in software, where the chip
answers in hardware; an abnormally long exchange then reveals that the answer does not come from the expected
product. The maximum duration to declare depends on the command, the card and the reader, and is chosen by the
application or the card extension.

[[sec_apdu_construction_rules]]
=== APDU construction rules

The APDU commands carried by <<type_ApduRequest,`ApduRequest`>> MUST strictly comply with
<<ref_iso7816,ISO/IEC 7816-3>>. In particular, a case 4 command -- one carrying data in both directions -- MUST
include the `Le` field. It is RECOMMENDED to set this field to `00h`.

[[sec_limitations_constraints]]
=== Limitations and constraints

The Card API does not allow the transmission of the following APDU commands to a card to be requested:

* *Select Application* by DF name: the selection of a card application is managed exclusively through a
  <<type_CardSelectionRequest,`CardSelectionRequest`>>;
* *Get Response*: the status words `61XYh` and `6CXYh` are handled automatically by the reader implementation, which
  issues a *Get Response* command or re-issues the previous command with the expected `Le` field.

=== API Interfaces

[[type_ProxyReaderApi]]
==== Proxy Reader API

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Name       | `ProxyReaderApi`
| Kind       | Interface
| Namespace  | `card`
| Since      | 1.0
| Purpose    | Reader-side facet exposing APDU transmission and channel-closure operations to card extensions.
|===

A `ProxyReaderApi` and the `CardReader` interface defined in <<ref_cna_tr,CNA-TR-API>> are two facets of the same
underlying reader; they are separated so that only the *internal* dialog with cards is exposed to extension
modules. `ProxyReaderApi` is the *backside* of `CardReader`: it is the reader able to transmit card requests and
having control over the physical channel.

The proxy reader uses the *smart card SPI* received as parameter to identify the target of every operation: it
extracts the channel information (when the dynamic type is <<type_MultichannelSmartCardSpi,
`MultichannelSmartCardSpi`>>) and verifies the active state of the smart card (see
<<sec_smartcard_role,the role of the smart-card SPI parameter>>) before performing any exchange.

[[sec_smartcard_role]]
.Role of the smart-card SPI parameter
The three operations of `ProxyReaderApi` receive a smart-card SPI parameter. This parameter is *not* a mere
vehicle for the channel number. It plays up to three roles:

. **Channel routing** (only when the dynamic type is <<type_MultichannelSmartCardSpi,
  `MultichannelSmartCardSpi`>>): the logical channel number is read via `getChannel()` and used to route the
  APDU exchange or the closure on the correct logical channel. When the parameter is a base `SmartCardSpi` (not a
  `MultichannelSmartCardSpi`), the exchange is addressed to the basic channel (channel `0`).
. **Active-state check**: the active state of the smart card is verified before any exchange
  (`SmartCard.isActive()` is `true` per <<ref_cna_tr,CNA-TR-API>>). If it is not active, a
  `CardBrokenCommunication` is raised without contacting the card.
. **Deactivation**: when the situation requires it (typically after a communication failure or after an explicit
  channel closure), <<op_SmartCardSpi_deactivate,`SmartCardSpi.deactivate`>> is called so that the deactivation is immediately
  visible to the application via `SmartCard.isActive() == false`.

Roles 2 and 3 are common to `SmartCardSpi` and `MultichannelSmartCardSpi`; role 1 is specific to the multi-channel
variant.

[[sec_errors]]
=== Errors

Every error defined below carries two properties: `message` (`String`), which describes the condition, and
`cause` (`Any?`), the underlying error that triggered it, `null` when there is none. They are not
restated for each error.

The APDU-level errors -- <<type_ReaderBrokenCommunication,`ReaderBrokenCommunication`>>,
<<type_CardBrokenCommunication,`CardBrokenCommunication`>>, <<type_UnexpectedStatusWord,`UnexpectedStatusWord`>>
and <<type_ApduExchangeDurationExceeded,`ApduExchangeDurationExceeded`>> -- additionally carry
`cardResponse` (`CardResponse?`), the responses collected before the failure occurred, and
`isCardResponseComplete` (`Boolean`), which indicates whether every prepared APDU produced a response.
