== Abstract

This document is the official technical specification of the **{spec-name}** standardised
by the **{organization}** ({short-name}).
It defines, in a language-agnostic way, the interfaces, classes, enumerations, exceptions, structural
relationships and behavioural requirements that any conforming implementation of the {spec-name} MUST satisfy.

The {spec-name} is the *underside* of the *Terminal Reader API* ([CNA-TR-API]). It defines the contract used
internally by reader implementations and by card extension modules to exchange APDU-level data with cards, while
the *Terminal Reader API* remains the public-facing surface used by terminal applications.

== Introduction

=== Purpose

The {spec-name} defines the contract by which:

* a *reader implementation* MUST expose an APDU transmission interface (the *proxy reader*) so that selection
  managers and card transaction managers can exchange data with cards in a uniform way,
* a *card extension* MUST expose its selection process (request preparation and response parsing) so that the
  selection manager defined by [CNA-TR-API] can drive it,
* exceptions raised at APDU exchange level MUST carry the responses already received before the failure.

The API is *internal*: terminal applications MUST NOT use it directly. It is the contract that allows reader
implementations and card extensions written by independent vendors to interoperate.

=== Scope

This specification covers:

* the APDU request and response data carriers,
* the selection request and response data carriers,
* the proxy-reader contract through which APDUs are transmitted,
* the SPI implemented by card extensions to drive selection,
* the channel-control policy applied after a card request,
* the family of exceptions raised at APDU exchange level.

The following topics are *out of scope*:

* the public reader interface exposed to terminal applications (covered by [CNA-TR-API]),
* the parsing of APDU payloads (deferred to specific card extension specifications).

=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it raises exceptions exclusively of the types defined in <<sec_exceptions>> for the situations described,
. when implementing an adapter of <<type_ProxyReaderApi,`ProxyReaderApi`>>, it MUST also implement the
  `CardReader` interface of [CNA-TR-API]; when implementing an adapter of
  <<type_CardSelectionExtensionSpi,`CardSelectionExtensionSpi`>>, it MUST also implement the
  `CardSelectionExtension` interface of [CNA-TR-API]; when implementing an adapter of
  <<type_SmartCardSpi,`SmartCardSpi`>>, it MUST also implement the `SmartCard` interface of [CNA-TR-API].

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHALL**, **SHALL NOT**, **SHOULD**,
**SHOULD NOT**, **RECOMMENDED**, **MAY** and **OPTIONAL** are to be interpreted as described in **RFC 2119** and
**RFC 8174** when, and only when, they appear in all capitals.

== Terms, Definitions and Abbreviations

=== Terms and Definitions

[cols="1,4", options="header"]
|===
| Term              | Definition

| APDU              | Application Protocol Data Unit, the message format used between the terminal and the card (ISO/IEC 7816-4).
| Case 4 APDU       | APDU command that carries data in both directions; the `Le` field is mandatory and SHALL be set to `00h`.
| Card Extension    | Software module providing the card-specific dialogue with a card family (e.g. Calypso).
| Logical Channel   | Software-level communication path established with a card after a successful selection.
| Physical Channel  | Hardware-level communication path between the reader and the card.
| Proxy Reader      | Reader-side facet exposing APDU transmission to extension layers, by opposition to the public reader interface presented to terminal applications.
| Status Word (SW)  | Two-byte trailer of an APDU response indicating the outcome of the command.
| SPI               | Service Provider Interface -- a set of interfaces designed to be implemented by an extension module.
|===

[[type_CardResponseApi]]
==== CardResponseApi

[cols="1h,4", grid=rows, frame=ends]
|===
| Kind     | Interface
| Package  | `card`
| Since    | 1.0.0

some responses MAY be missing (e.g. the card was removed during processing, or processing stopped after an

| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]

| Since       | 1.0.0
| Description | Indicates the state of the logical channel after the request has been processed.

[[type_ProxyReaderApi]]
==== ProxyReaderApi

[cols="1h,4", grid=rows, frame=ends]
|===
| Kind     | Interface
| Package  | `card`
| Since    | 1.0.0
| Purpose  | Reader-side facet exposing APDU transmission and physical-channel control. The *underside* of the [CNA-TR-API] `CardReader` interface.

===== Operations

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `transmitCardRequest(cardRequest: CardRequestSpi, channelControl: ChannelControl) -> CardResponseApi`
| Since       | 1.0.0
| Description
| Transmits a <<type_CardRequestSpi,`CardRequestSpi`>>, applies the supplied <<type_ChannelControl,`ChannelControl`>>
  policy and returns a <<type_CardResponseApi,`CardResponseApi`>>. The APDUs in the request MUST be sent in order;
  the corresponding responses are appended to the returned object.

  In case of an error when sending an APDU (communication failure, unexpected status word), an
  <<type_AbstractApduException,`AbstractApduException`>> MUST be thrown. Any responses to previously transmitted
  APDU commands MUST be attached to this exception so that the calling application can tolerate card tearing or
  enforce strict APDU-by-APDU control (see <<type_CardRequestSpi,`CardRequestSpi.stopOnUnsuccessfulStatusWord`>>).
| Parameters
| `cardRequest`     -- the card request. +
  `channelControl`  -- the channel control policy to apply.
| Returns     | A non-`null` <<type_CardResponseApi,`CardResponseApi`>>.
| Throws
| `IllegalArgumentException` -- if any parameter is `null`. +
  `ReaderBrokenCommunicationException` -- if the communication with the reader has failed. +
  `CardBrokenCommunicationException` -- if the communication with the card has failed. +
  `UnexpectedStatusWordException` -- if any of the APDUs returned an unexpected status word and the request requires checking them.
|===

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `releaseChannel() -> void`
| Since       | 1.0.0
| Description | Releases the communication channel previously established with the card.
| Throws      | `ReaderBrokenCommunicationException` -- if the communication with the reader has failed.
|===

[[sec_exceptions]]
== Exceptions

All exceptions defined here are *checked* and MUST be declared by the operations that may raise them. Every
exception carries the responses already received from the card before the failure occurred, so that the calling
layer can tolerate partial responses.

[[sec_behaviours]]
== Behavioural Requirements

. The order of APDUs in a <<type_CardRequestSpi,`CardRequestSpi`>> MUST be preserved by the proxy reader, and so
  MUST the order of responses in the resulting <<type_CardResponseApi,`CardResponseApi`>>.
. The set of successful status words declared by an <<type_ApduRequestSpi,`ApduRequestSpi`>> MUST contain at least
  `9000h`.
. The set of successful selection status words declared by a <<type_CardSelectionRequestSpi,`CardSelectionRequestSpi`>>
  MUST contain at least `9000h`.
. When `stopOnUnsuccessfulStatusWord` returns `true`, transmission of the remaining APDUs MUST stop at the first
  unsuccessful status word; the responses already received MUST be returned in the exception payload.
. The `isCardResponseComplete` flag of any <<type_AbstractApduException,`AbstractApduException`>> MUST reflect
  exactly whether the number of responses already received equals the number of APDU requests in the originating
  <<type_CardRequestSpi,`CardRequestSpi`>>.
. An adapter implementing <<type_ProxyReaderApi,`ProxyReaderApi`>> MUST also implement [CNA-TR-API] `CardReader`;
  similarly for <<type_CardSelectionExtensionSpi,`CardSelectionExtensionSpi`>>/`CardSelectionExtension` and
  <<type_SmartCardSpi,`SmartCardSpi`>>/`SmartCard`.
