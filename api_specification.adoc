== Abstract

This document is the official technical specification of the **{spec-name}** standardised
by the **{organization}** ({short-name}).
It defines, in a language-agnostic way, the interfaces, classes, enumerations, exceptions, structural
relationships and behavioural requirements that any conforming implementation of the {spec-name} MUST satisfy.

The {spec-name} is the *underside* of the *Terminal Reader API* (<<ref_cna_tr,CNA-TR-API>>). It defines the *internal*
contract used by reader implementations and by card extension modules to exchange APDU-level data with cards,
while the *Terminal Reader API* remains the public-facing surface used by terminal applications.

== Introduction

=== Purpose

The {spec-name} defines the *internal* contract by which:

* a *reader implementation* MUST expose an APDU transmission interface (the *proxy reader*) so that selection
  managers and card transaction managers can exchange data with cards in a uniform way,
* a *card extension* MUST expose its selection process (request preparation and response parsing) so that the
  selection manager defined by <<ref_cna_tr,CNA-TR-API>> can drive it,
* APDU-level exceptions carry the responses already received before the failure together with any duration
  information required to enforce the APDU exchange execution-time bounds.

The API is *internal*: terminal applications MUST NOT use it directly. It is the contract that allows reader
implementations and card extensions written by independent vendors to interoperate.

=== Scope

This specification covers:

* the APDU request and response data carriers, including the per-request duration bound and per-response measured
  duration used to control the APDU exchange execution time,
* the selection request and response data carriers, including the multi-channel-aware channel information,
* the proxy-reader contract through which APDUs are transmitted, including the multi-channel transmission and
  closure operations,
* the SPI implemented by card extensions to drive selection,
* the SPI implemented by card extensions to represent a selected smart card, including the multi-channel variant,
* the family of exceptions raised at APDU exchange level.

The following topics are *out of scope*:

* the public reader interface exposed to terminal applications (covered by <<ref_cna_tr,CNA-TR-API>>),
* the parsing of APDU payloads (deferred to specific card extension specifications),
* the protocol-level cryptographic security mechanisms handled by card extensions such as the
  Calypso Card API.

=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it raises exceptions exclusively of the types defined in <<sec_exceptions>> for the situations described,
. when implementing an adapter of <<type_ProxyReaderApi,`ProxyReaderApi`>>, it MUST also implement the
  `CardReader` interface of <<ref_cna_tr,CNA-TR-API>>; when implementing an adapter of
  <<type_CardSelectionExtensionSpi,`CardSelectionExtensionSpi`>>, it MUST also implement the
  `CardSelectionExtension` interface of <<ref_cna_tr,CNA-TR-API>>; when implementing an adapter of
  <<type_SmartCardSpi,`SmartCardSpi`>>, it MUST also implement the `SmartCard` interface of <<ref_cna_tr,CNA-TR-API>>.

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
**MAY** and **OPTIONAL** are to be interpreted as described in <<ref_rfc2119,RFC 2119>> and <<ref_rfc8174,RFC 8174>> when, and only when,
they appear in all capitals.

In conformance with <<ref_rfc2119,RFC 2119>>, **SHALL** is equivalent to **MUST**; this specification uses **MUST** exclusively in
order to avoid ambiguity.

==== Operation contracts

To avoid repetition, the following rules apply to every operation table in <<sec_specification>> and are therefore
not restated for each operation:

* *Non-`null` arguments.* Unless explicitly stated otherwise, every input parameter MUST be non-`null`. An
  implementation MUST raise `IllegalArgumentException` if a `null` value is supplied. This implicit `null` check is
  not repeated in the *Throws* row, which states `None.` when no other exception can occur.
* *Non-`null` results.* Unless the return type is marked nullable (`T?`) or the *Returns* row states otherwise, an
  operation returns a non-`null` value.
* *Collections.* Unless the return type is marked nullable (`T?`), an operation whose return type is a collection
  (e.g. `list`, `set`, `map`) returns an empty collection rather than `null`.

==== Concurrency

Unless explicitly stated otherwise, the stateful types defined by this specification are *not* thread-safe. A given
instance MUST be accessed from a single thread at a time; concurrent use of the same instance without external
synchronisation results in undefined behaviour. Distinct instances MAY be used concurrently.

== Terms, Definitions and Abbreviations

=== Terms and Definitions

[cols="1,4", options="header"]
|===
| Term              | Definition

| APDU              | Application Protocol Data Unit, the message format used between the terminal and the card (<<ref_iso7816,ISO/IEC 7816-4>>).
| Case 4 APDU       | APDU command that carries data in both directions; the `Le` field is mandatory and MUST be set to `00h`.
| Card Extension    | Software module providing the card-specific dialog with a card family (e.g. Calypso).
| Logical Channel   | Software-level communication path established with a card after a successful selection.
| Basic Channel     | The default logical channel (channel `0`) of an ISO/IEC 7816-4 card.
| Physical Channel  | Hardware-level communication path between the reader and the card.
| Proxy Reader      | Reader-side facet exposing APDU transmission to extension layers, by opposition to the public reader interface presented to terminal applications.
| Status Word (SW)  | Two-byte trailer of an APDU response indicating the outcome of the command.
| SPI               | Service Provider Interface -- a set of interfaces designed to be implemented by an extension module.
|===

=== Multi-channel design

The {spec-name} exposes the multi-channel capability of ISO/IEC 7816-4 cards through:

* a dedicated SPI sub-type <<type_MultichannelSmartCardSpi,`MultichannelSmartCardSpi`>> that carries the channel
  number of each active smart card,
* dedicated proxy-reader operations
  <<op_transmitCardRequestAndCloseChannel,`transmitCardRequestAndCloseChannel`>> and
  <<op_closeChannel,`closeChannel`>> that target a specific channel by passing the corresponding
  `MultichannelSmartCardSpi`.

The single-channel transmission operation <<op_transmitCardRequest,`transmitCardRequest`>> accepts the base
<<type_SmartCardSpi,`SmartCardSpi`>> and serves both the single-channel and the multi-channel use case (the
implementation extracts the channel information from the dynamic sub-type when needed).

=== APDU exchange execution-time control

To enable software-level control of the APDU exchange execution time, this specification carries:

* an *optional* per-request duration bound on <<type_ApduRequestSpi,`ApduRequestSpi`>>
  (<<op_getApduExchangeMaxDuration,`getApduExchangeMaxDuration`>>),
* an *optional* per-response effective duration on <<type_ApduResponseApi,`ApduResponseApi`>>
  (<<op_getApduExchangeDuration,`getApduExchangeDuration`>>),
* a dedicated exception <<type_ApduExchangeDurationExceededException,
  `ApduExchangeDurationExceededException`>> raised when the effective duration exceeds the declared bound.

[[type_ProxyReaderApi]]
==== Proxy Reader API

[cols="1h,4", grid=rows, frame=all]
|===
| Kind     | Interface
| Namespace  | `card`
| Since    | 1.0
| Purpose  | Reader-side facet exposing APDU transmission and channel-closure operations to card extensions.
|===

An implementation of `ProxyReaderApi` MUST also implement the `CardReader` interface defined in <<ref_cna_tr,CNA-TR-API>>. The
two facets share the same underlying reader; they are separated so that only the *internal* dialog with cards
is exposed to extension modules.

The proxy reader uses the *smart card SPI* received as parameter to identify the target of every operation: it
extracts the channel information (when the dynamic type is <<type_MultichannelSmartCardSpi,
`MultichannelSmartCardSpi`>>) and verifies the active state of the smart card (see
<<sec_smartcard_role,the role of the smart-card SPI parameter>>) before performing any exchange.

[[sec_smartcard_role]]
.Role of the smart-card SPI parameter
The three operations of `ProxyReaderApi` receive a smart-card SPI parameter. This parameter is *not* a mere
vehicle for the channel number. It plays up to three roles:

. **Channel routing** (only when the dynamic type is <<type_MultichannelSmartCardSpi,
  `MultichannelSmartCardSpi`>>): the logical channel number is read via `getChannel()` and used to route the
  APDU exchange or the closure on the correct logical channel.
. **Active-state check**: the proxy reader MUST verify, before performing any exchange, that the smart card is
  still active (`SmartCard.isActive()` is `true` per <<ref_cna_tr,CNA-TR-API>>). If it is not, the proxy reader MUST raise
  `CardBrokenCommunicationException` without contacting the card.
. **Deactivation**: when the situation requires it (typically after a communication failure or after an explicit
  channel closure), the proxy reader MUST invoke <<op_deactivate,`SmartCardSpi.deactivate`>> so that the
  deactivation is immediately visible to the application via `SmartCard.isActive() == false`.

Roles 2 and 3 are common to `SmartCardSpi` and `MultichannelSmartCardSpi`; role 1 is specific to the multi-channel
variant.

[[op_closeChannel]]

| Throws

  <<type_CardBrokenCommunicationException,`CardBrokenCommunicationException`>> -- if communication with the card is broken.
|===

[[op_transmitCardRequest]]
===== Transmit Card Request

[cols="1h,4", grid=rows, frame=all]

| `transmitCardRequest(cardRequest: CardRequestSpi, smartCard: SmartCardSpi) -> CardResponseApi`
| Since       | 3.0
| Description
| Transmits the provided <<type_CardRequestSpi,`CardRequestSpi`>> targeting the smart card identified by

[[sec_behaviours]]
== Behavioural Requirements

=== Active-state contract

. A `ProxyReaderApi` operation that receives a smart-card SPI parameter MUST check the active state of the
  smart card *before* performing any exchange with the card.
. If the smart card is no longer active, the operation MUST raise `CardBrokenCommunicationException` and MUST
  NOT contact the card.

=== Channel routing

. When a `ProxyReaderApi` operation receives a `MultichannelSmartCardSpi`, the implementation MUST use the value
  returned by `getChannel()` to route the APDU exchange or the closure on the corresponding logical channel.
. When `transmitCardRequest` is called with a base `SmartCardSpi` whose dynamic type is *not*
  `MultichannelSmartCardSpi`, the implementation MUST address the basic channel (channel `0`).

=== Channel closure

. `closeChannel` and `transmitCardRequestAndCloseChannel` MUST close the targeted logical channel and MUST then
  invoke `deactivate()` on the smart card.
. `closeChannel` MUST be idempotent.

=== Duration measurement

. If `ApduRequestSpi.getApduExchangeMaxDuration()` returns a non-`null` value, the proxy reader MUST measure the
  effective duration of the APDU exchange and MUST raise `ApduExchangeDurationExceededException` if the bound
  is exceeded.
. If the bound is `null`, the duration measurement is OPTIONAL. The implementation MAY still expose a measured
  duration on the corresponding `ApduResponseApi`; if the measurement is not available, the response operation
  MUST return `null`.
